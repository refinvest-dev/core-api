# Trading Analytics Result Integrity V1

This document defines `TRADING_ANALYTICS_RESULT_SCHEMA_V1` and `TRADING_ANALYTICS_RESULT_HASH_V1`. Computation formulas remain in [TRADING_ANALYTICS](TRADING_ANALYTICS.md), input rules in [input identity](TRADING_ANALYTICS_INPUT_IDENTITY.md), and transport in [delivery](TRADING_ANALYTICS_RESULT_DELIVERY.md). The Compute Engine `MetricResult` is the lossless source for the wire projection; Core validates structure, identities, references and hashes without recalculating the financial formula.

## Public sections and types

A completed payload contains **exactly** six public arrays: `outcomeClassifications`, `observations`, `metrics`, `relations`, `evidenceMembership`, `findings`. It does not resend full ReviewUnits. The Core resolves every `reviewUnitId` against the pinned published LedgerRevision's reconciliation manifest; every allocation and canonical record reference must resolve there and every source snapshot reference must resolve in the ledger artifact. Unknown/duplicate references fail publication. `createdAt` and `terminalAt` are transport metadata, never observation time or a logical digest input.

Each Metric is one of three `definitionId`-discriminated wire types. All share `metricId` (stable `definitionId` in V1), `definitionId`, `definitionVersion`, `status`, `findingEligibility`, `requiredCapabilities`, `populationCount`, `eligibleCount`, `excludedCount`, `excludedReasonCounts`, `scalarInputs`, `relationIds`, `membershipIds`, `values`, `metricHash`. Exactly one of each definition is required. `populationCount=eligibleCount+excludedCount`; `excludedReasonCounts` count distinct excluded ReviewUnits per reason, so their sum can exceed `excludedCount`. Status and sample precedence are those of ADR-060; a metric with an actual zero remains AVAILABLE when its eligibility is satisfied. Missing capability and insufficient sample are normal completed Metric states. `requiredCapabilities` is the definition's required set, not a copy of the manifest's global capability array.

`ENTRY_WITHIN_WINDOW_AFTER_LOSS.values` has `eligibleLossCount`, `lossWithEntryCount`, `relatedEntryCount`, same/different symbol and instrument counts, nullable `entryWithinWindowRate`, nullable `elapsedTimeDistribution`. The Engine's `sameSymbolCount`/`differentSymbolCount` compare pinned `instrumentId` and count loss units with at least one related entry of that kind; `sameInstrumentRelatedEntryCount`/`differentInstrumentRelatedEntryCount` count related entry members. `INITIAL_EXPOSURE_CHANGE_AFTER_LOSS.values` has pair/increased/equal/decreased counts, nullable median next entry/loss ratio, nullable ratio and percentage delta distributions, currency-keyed absolute delta distributions, and a sorted `pairs` array containing loss/entry IDs, currency, two notionals, absolute delta, ratio, percentage delta, same instrument/direction flags, baseline episode IDs, nullable baseline median/ratio/delta and nullable baseline reason. `WIN_LOSS_HOLDING_DURATION_DIFFERENCE.values` has win/loss/breakeven/unavailable counts, nullable win/loss distributions, nullable median difference in microseconds, nullable median ratio and nullable ratio unavailable reason. Nullable fields are **required** and explicit `null` means undefined under the Metric definition; zero is the string rational `0/1` or decimal `0`, never null. Re-entry rate/distribution are non-null only when status AVAILABLE; exposure aggregate median/distributions are non-null and currency distributions populated only when AVAILABLE, while per-pair data remains; holding distributions/difference/ratio are non-null only when AVAILABLE, except median ratio is null with `medianRatioReason=ZERO_DENOMINATOR` when the win median is zero. Baseline reason is null when sufficient nonzero baseline exists, otherwise exactly `INSUFFICIENT_PRIOR_BASELINE` or `ZERO_DENOMINATOR` per ADR-060.

Each distribution has `count`, and `minimum`, `p25`, `median`, `p75`, `maximum`, `mean` as exact rational or null. Empty distribution has count 0 and all six null; nonempty has all six non-null. Rational is `{numerator,denominator}` with canonical coprime signed integer numerator, positive denominator, `0/1` for zero. Decimal is canonical plain base-10 string: no exponent, `-0` forbidden, no trailing fractional zeros, no unnecessary leading zero; input source lexeme belongs only in `scalarInputs` and is not used for Decimal values. Duration is a signed rational number of microseconds for differences, nonnegative integer microseconds for observed elapsed time. JSON number is used only for safe integers (counts, source row, microseconds); no floating point financial value.

`OutcomeClassification` is keyed by `reviewUnitId` and carries outcome, nullable net trading PnL and settlement currency, sorted allocated reported PnL and fee tuples (record ID, decimal, currency), and a `membershipId` that resolves to evidence. When multiple Engine MetricResults classify the same ReviewUnit, Compute merges identical public projections into one outcome item; conflicting projections fail `RESULT_ITEM_CONFLICT`. `Observation` carries definition/version, sorted subject IDs, observedAt, all matching Metric `scalarInputs` for its subject IDs as sorted attributes, relation IDs, and membership IDs. Re-entry emits one observation per eligible loss relation: `observationId=definitionId:lossId:relationId`, subjects `[lossId]`, observedAt **loss closedAt**, that relation ID and loss SUBJECT membership. Exposure emits one per pair: `observationId=definitionId:lossId:entryId`, subjects sorted `[lossId,entryId]`, observedAt **related entry openedAt**, linked re-entry relation ID and exposure SUBJECT/COMPARISON memberships. Holding emits one per eligible win/loss episode: `observationId=definitionId:episodeId:0`, subjects `[episodeId]`, observedAt **episode closedAt**, no relation ID, and its SUBJECT or COMPARISON membership. A missing required timestamp excludes the unit per Metric definition; result generation time is never substituted. `Relation` is keyed by `relationId = lossReviewUnitId + ':ENTRY_WITHIN_WINDOW_AFTER_LOSS'`, carries loss closedAt, sorted candidate entry ID/role/openedAt/membership ID tuples, sorted related entry IDs, nullable elapsed microseconds, and relation membership IDs. Candidate roles and exclusions preserve the Engine's `RelationCandidate` output, including selection boundaries.

`EvidenceMembership` is keyed by `membershipId = metricId + ':' + reviewUnitId + ':' + role + ':' + reasonOrEmpty`. Role is `SUBJECT`, `COMPARISON`, `EXCLUDED`, `RELATION_CANDIDATE`, `RELATED_ENTRY`, `PRIOR_BASELINE`, or `SELECTION_BOUNDARY`. Engine `SUPPORTING` maps to `SUBJECT`, `EXCLUDED_CANDIDATE` to `EXCLUDED`, and `COMPARISON`/`SELECTION_BOUNDARY` retain their names. Each relation candidate becomes `RELATION_CANDIDATE`, except `SELECTED_EARLIEST` additionally gets `RELATED_ENTRY`; the candidate retains its original relation role enum. A prior baseline episode ID gets `PRIOR_BASELINE` even if it also has another role. It carries metric/reviewUnit IDs, role, sorted reasons (empty for nonexcluded), sorted allocation IDs, sorted canonical record IDs and sorted source evidence snapshot IDs. An Engine membership with multiple reasons creates one EXCLUDED membership **per reason**; `exclusionReason` is that reason or null. Duplicate membership identity is invalid, even if contents match. `allocationRecordIds` name stable `InternalPositionAllocation.allocationId`, not execution IDs; each allocation maps to a canonical `recordId`. References that have no allocation may still name the ReviewUnit's `evidenceRecordIds` directly. The chain is Metric → observation/relation/membership → ReviewUnit → allocation → canonical record → source evidence. An opaque `evidenceReference` string is not used.

`findings` is **exactly `[]`** for `findingRuleSetVersion=TRADING_FINDING_RULES_DISABLED_V1`. Metric finding eligibility is still computed. This is a versioned Metric-only rule set, not an accidental absence of implementation. Any nonempty Findings with this version fails schema/integrity validation. A future rule set requires a new version and a new TradingAnalysisRun; never rewrite V1 results.

## Canonical projections and hashes

All hashes are lowercase SHA-256 of UTF-8 RFC 8785 JCS, no BOM/newline. Reject duplicate JSON keys, unsafe integers, noncanonical decimals/rationals, duplicate item identities and unsorted nested sets. Unicode is not normalized. Sorted public arrays compare string keys by UTF-16 code units, matching JCS object-key ordering; all ID arrays are sorted and unique; currency maps have JCS key order. Null remains explicit when schema requires it. `metricHash = sha256(JCS(full typed metric object with metricHash removed))`. It includes all scalar inputs, typed values, definition/version/status/eligibility, capabilities, counts/reasons and relation/membership IDs. Changing any public Metric field changes its metricHash.

| Section | Item identity / sort key | Nested order |
|---|---|---|
| `OUTCOME_CLASSIFICATIONS` | `reviewUnitId` | allocation tuples by `(recordId,currency)` |
| `OBSERVATIONS` | `observationId` | subject/membership IDs sorted; attributes by name |
| `METRICS` | `metricId` | capabilities, scalar inputs `(reviewUnitId,name,value)`, reference IDs sorted; pairs `(lossId,entryId,currency)`, baseline IDs sorted |
| `RELATIONS` | `relationId` | candidates `(openedAt,entryId,role)` with null last; related IDs sorted |
| `EVIDENCE_MEMBERSHIPS` | `membershipId` | reasons and all reference ID arrays sorted |
| `FINDINGS` | `findingId` | V1 exactly empty |

`sectionHash = lowercaseHex(SHA-256(UTF-8(JCS(sorted public section items))))`, including the empty array hash for an empty section. A section digest is `{sectionType,itemCount,hashSpecificationVersion,sectionHash}`; `hashSpecificationVersion=TRADING_ANALYTICS_RESULT_HASH_V1`. `sectionDigests` is exactly six entries sorted by section type's wire name. `AnalyticsResultCounts` has `outcomeClassificationCount`, `observationCount`, `metricCount`, `relationCount`, `evidenceMembershipCount`, `findingCount`. These are structural array lengths, **not** a cross-Metric population. `metricCount=3`, `findingCount=0` in V1. `evidenceHash` equals the `EVIDENCE_MEMBERSHIPS` section hash.

The exact `AnalyticsResultDigestManifest` root is `{resultHashSpecificationVersion,resultSchemaVersion,inputHash,inputHashSpecificationVersion,analysisConfigHash,targetVersionSet,counts,sectionDigests}`. `resultHash = lowercaseHex(SHA-256(UTF-8(JCS(AnalyticsResultDigestManifest))))`. The embedded manifest must exactly equal the projection of payload fields; its counts and digests are checked against actual sections **before** its hash. The logical result excludes job/Run IDs, attempt, deletion generation, payload ID, locator/expiry, delivery policy, createdAt and terminalAt. A retry with identical semantic input must yield identical resultHash.

Core verification order: (1) check current Run/attempt/generation and descriptor identity; (2) enforce negotiated bytes and SHA-256; (3) strict JSON/schema and exact version pins; (4) descriptor↔payload identity/count/hash equality; (5) recompute each metricHash; (6) check structural counts against arrays and exactly three Metric IDs; (7) resolve every membership, relation, ReviewUnit, allocation, record and source evidence reference; (8) recompute six section digests/evidenceHash; (9) rebuild manifest and resultHash; (10) compare-and-set publish, then ACK. Fail with `RESULT_TRANSPORT_HASH_MISMATCH`, `RESULT_SCHEMA_UNSUPPORTED`, `RESULT_COUNT_MISMATCH`, `EVIDENCE_REFERENCE_INVALID`, `RESULT_SECTION_HASH_MISMATCH`, or `RESULT_HASH_MISMATCH` as applicable, without publication. Core never repairs a received count/hash before verification. The [fixed vector](../fixtures/trading-analytics/result-integrity-v1.json) is normative for hash bytes.
